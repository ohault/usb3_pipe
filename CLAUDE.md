# Project Memory (ohault/usb3_pipe fork)

Context for Claude sessions working on this fork. The general rules are in [AGENTS.md](AGENTS.md) and
[CONTRIBUTING.md](CONTRIBUTING.md) (tests, coding style, commits, hardware safety), which follow LiteX's
[LiteX for AI Agents](https://github.com/enjoy-digital/litex/blob/master/doc/wiki/LiteX-for-AI-Agents.md):
read that page first for LiteX itself (repository map, `--build --no-compile`, `litex_sim`,
`litex_server`/`RemoteClient`, LiteScope, the `litex_mcp` server, the agent skills in LiteX
`doc/agent/skills/`).

## LiteX Projects We Work On

- **USB3-PIPE** (this repository, fork of [enjoy-digital/usb3_pipe](https://github.com/enjoy-digital/usb3_pipe)):
  USB 3.2 Gen 1x2 (2x5Gbps, two lanes) on the LiteX Acorn Baseboard Mini + SQRL Acorn CLE-215+
  (Artix7 GTP), following [issue #140](https://github.com/enjoy-digital/usb3_pipe/issues/140).
- **LiteX Acorn Baseboard Mini** ([enjoy-digital/litex-acorn-baseboard](https://github.com/enjoy-digital/litex-acorn-baseboard)):
  two SFP cages (SFP-0 = J3, closest to the M.2; SFP-1 = J8, closest to the SATA), FTDI on USB-C J7
  (FT2232H on the user's boards, FT4232H on other revisions: JTAG channel A, UART channel B;
  `bench/acorn_ftdi.py`), J10 Pico-EZmate to the Acorn JTAG, power on USB-C J9.
- LiteX, Migen, LiteICLink, LiteX-Boards: dependencies (LiteX `master`); fixes needed there go
  upstream (see AGENTS.md "Contribute back").

## Environment Notes (Claude Code cloud sessions)

- No Vivado: elaborate (`test/test_targets.py` `elaborate()`), never claim a timing result.
- `pip` installs from git and `litex_setup.py` may be refused: the preinstalled PyPI migen (0.9.2)
  cannot simulate `SyncFIFO` memories (about 78 tests fail identically on `master`: compare the
  failure lists with an upstream worktree before blaming a change).
- `sim.py` needs `pythondata_misc_tapcfg` (only for the LiteX sim Ethernet modules): a local stub
  package on `PYTHONPATH` (header + functions returning -1) is enough.
- Remote branch deletions are refused by the session git proxy: the user deletes/renames branches.
- Hardware from a cloud session: the user's NUC runs a Claude Code session through Remote Control
  (`claude remote-control`, listed by list_sessions, title `ohault-nuc7i7dnhe-*`, tag
  remote-control-cli). This session sends it tasks with send_message (allowed once by the user on a
  trusted device) and reads its results with list_events (kinds result): its own send_message back is
  refused. No computer folder is offered to cloud sessions on this account (list_computer_folders
  empty). Self check-ins (send_later) fail with ACCESS_DENIED: the user asks "check again".
- Upstream docs are in the manual (`doc/manual/`, checks: `python3 doc/manual/build.py --check`,
